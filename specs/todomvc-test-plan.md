## 1. Цель и объём

Проверить функциональность списка задач: добавление, редактирование, отметку выполнения, удаление, фильтрацию, счётчик, сохранение состояния и маршрутизацию.

**Вне объёма:** производительность, безопасность, кросс-доменные сценарии. Бэкенда у приложения нет, поэтому API-тестов нет.

## 2. Об устройстве приложения

- Бэкенда нет, данные хранятся в `localStorage` под ключом `react-todos` в формате
  `[{ "id": "<uuid>", "title": "…", "completed": false }]`.
- Маршрутизация через hash: `#/`, `#/active`, `#/completed`.
- Вверху страницы жёлтый баннер «This is just a demo of TodoMVC for testing», это нормально.
- Каждый тест начинается с чистого состояния: новый `browserContext` в Playwright даёт пустой `localStorage`.

## 3. Локаторы

Приоритет: role / label / placeholder / test-id. CSS-классы используются только там, где других вариантов нет.

| Элемент | Рекомендуемый локатор | Запасной вариант (CSS) |
|---|---|---|
| Поле ввода новой задачи | `getByPlaceholder('What needs to be done?')` | `.new-todo` |
| Элемент списка | `getByTestId('todo-item')` | `.todo-list li` |
| Текст задачи | `getByTestId('todo-title')` | `.todo-list label` |
| Чекбокс задачи | `getByRole('checkbox', { name: 'Toggle Todo' })` | `.toggle` |
| Кнопка удаления (видна при hover) | `getByRole('button', { name: 'Delete' })` | `.destroy` |
| Поле редактирования | `getByRole('textbox', { name: 'Edit' })` | `.edit` |
| «Отметить все» | `getByLabel('Mark all as complete')` | `.toggle-all` |
| Счётчик | `getByTestId('todo-count')` | `.todo-count` |
| Фильтры | `getByRole('link', { name: 'All' / 'Active' / 'Completed' })` | `.filters a` |
| «Clear completed» | `getByRole('button', { name: 'Clear completed' })` | `.clear-completed` |
| Блоки main / footer | — | `.main`, `.footer` |

**Состояния элемента списка** (класс на `<li>`): `completed` означает, что задача выполнена, `editing` включён в режиме редактирования.

## 4. Тестовые данные

```ts
const TODO_ITEMS = ['buy some cheese', 'feed the cat', 'book a doctors appointment'];
```

Граничные значения: строка из пробелов, текст с пробелами по краям, спецсимволы и HTML (`<b>x</b> & "q" 😀`), длинная строка (500+ символов).

## 5. Приоритеты

- **P1** — критичный функционал (smoke), должен проходить всегда
- **P2** — основной функционал
- **P3** — граничные случаи, UI-детали

## 8. Рекомендации по реализации

- **Структура:** `tests/*.spec.ts`, один файл на раздел (`add.spec.ts`, `edit.spec.ts`, …), Page Object `TodoPage` в `tests/pages/`.
- **baseURL:** задать в `playwright.config.ts`: `use: { baseURL: 'https://demo.playwright.dev' }` → `page.goto('/todomvc')`.
- **Фикстура** `todoPage`, которая открывает приложение. Опционально сделать фикстуру с тремя заранее добавленными задачами.
- **Только web-first assertions**: `toHaveText`, `toHaveCount`, `toHaveClass`, `toBeVisible`, `toHaveURL`. Не использовать `allInnerTexts()` и `count()` в проверках: после клика по фильтру список перерисовывается асинхронно, и мгновенное чтение вернёт устаревшие данные. Проверено при исследовании приложения.
- **localStorage:** проверять через `page.waitForFunction` / `expect.poll` + `page.evaluate`.
- **Без `waitForTimeout`**: при правильных локаторах и assertions он не нужен.
- ID тест-кейса указывать в названии теста, например `test('TC-ADD-01 добавить одну задачу @smoke', …)`. Так тест легко связать со спецификацией.
